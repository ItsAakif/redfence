# Dataset card — RedFenceBench

Dataset version: `redfencebench-0.4.0` · seed `20260101` · licence Apache-2.0.

The 0.3.0 → 0.4.0 bump is a **provenance-schema/config change, not a content
change**: classic document content and content hashes are unchanged. It adds
four deterministic lifecycle configs (`lineage`, `existence`, `repair`,
`replication`; config version `redfencebench-configs-0.1.0`) under
`datasets/redfencebench/configs/`. They are separate JSON artifacts, not part
of `Corpus.manifest()`, and contain no cleartext canaries.

The 0.2.0 → 0.3.0 bump likewise changed only the manifest schema: manifest
schema `2` adds `acl_fingerprint`, hashed `canary_markers` and
`principal_entitlements`; no cleartext canary appears in a manifest.

## Composition

Fully synthetic, internally consistent multi-tenant corpus generated
deterministically by `datasets/redfencebench/generator.py`. The corpus is
**template-driven** (`build_corpus(seed, template=...)`): every template extends
the same `classic` skeleton, and the isomorphism contract
(`template_isomorphic`) guarantees the single development scenario runs
unchanged over all of them.

**Templates** (structural variation axes; the default is `classic`):

| Template | Adds | Varies |
|---|---|---|
| `classic` | — (the 0.1.0 corpus, byte-identical, content hashes pinned by test) | — |
| `secret_tier` | `secret`-classified vault document + `secret`-clearance officer principal + one lexically distant benign document | classification-tier depth, principal count, doc count |
| `three_tenant` | `t_gamma` with its own confidential canary document + reader | tenancy width, group composition (the secondary reader no longer carries a primary-tenant group) |

The `classic` skeleton:

- **Tenants:** `t_alpha` (Alpha Corp), `t_beta` (Beta Inc).
- **Principals:** `p_alpha_reader` (engineer, confidential), `p_alpha_lead`
  (engineer, confidential), `p_alpha_intern` (intern, internal clearance),
  `p_beta_reader` (engineer, confidential).
- **Documents:**
  - `doc_alpha_secret` — confidential, contains canary `CANARY_ALPHA_*`.
  - `doc_alpha_benign` — internal, benign.
  - `doc_beta_secret` — confidential, contains canary `CANARY_BETA_*`.
  - `doc_alpha_malicious` — internal, contains an indirect-injection payload.
- **Metadata:** per-chunk ACLs (tenant, classification, roles, groups, epoch),
  document provenance, versions, canaries, `malicious` label.
- **Expected outcomes:** security (deny) and benign (allow) outcomes are encoded
  by the authoritative ACL and the scenario's expected utility observation.

**Isomorphism contract** (asserted by `template_isomorphic` for every
template): canonical principals `p_<tenant>_reader|lead|intern` for the primary
tenant and `p_<tenant>_reader` for the secondary; exactly one confidential
document per anchor tenant, owning the `alpha` / `beta` canaries; the fixed
anchor phrases (`launch code` in the primary, `access token` in the secondary)
that let the hash embedder surface cross-tenant leakage; a malicious document in
the primary tenant. Templates provide **structural/topological diversity**
(tenancy width, classification tiers, doc/principal counts, group composition),
**not linguistic diversity** — anchor phrasing is intentionally shared so
detection keeps working; do not describe this corpus as linguistically diverse.

## Generation methodology

Line-based deterministic chunking; hash-based deterministic embeddings; no
randomness beyond the fixed seed used to derive canary suffixes. Regenerating
from the same seed reproduces identical content hashes.

## Manifest provenance

The corpus manifest uses schema `2`. Each document carries its `content_hash`
plus `acl_fingerprint` (a digest of the authoritative ACL) and `canary_markers`
(redacted/hashed, never cleartext). The manifest also records
`principal_entitlements`, a fingerprint per principal. The canonical manifest
digest is recorded in each run manifest as `corpus_manifest_sha256`, so a run
can be tied to the exact corpus provenance it measured. The checked-in artifacts
are the `classic` template; other templates are generated on demand.

## Lifecycle configs

`datasets/redfencebench/configs/` holds four deterministic, `classic`-derived
config artifacts (config version `redfencebench-configs-0.1.0`):

| File | Cases |
|---|---|
| `lineage.json` | source document × principal × derived kind, with expected `descendant`/`absent` |
| `existence.json` | twin-audit query, hidden source, visible principal, expected `same_response` |
| `repair.json` | document, principal and a `purge_cache`/`delete_memory`/`restore_acl`/`reingest` plan |
| `replication.json` | `replica`/`backup`/`retention` store and deletion-propagation policy |

Each file carries `config_version`, `kind`, `dataset_version`, `template`, `seed`
and `cases`, with sorted keys and no timestamps. They are generated by
`generate_configs()` (`--configs`, or as part of `--all`) and are pinned by
SHA-256 in `tests/test_dataset.py`.

## Splits

Template **families** are disjoint between development and held-out sets (no
random splitting of near-identical templates):

- **Dev (facet labels of the single revocation scenario, not independent
  executable families):** `revocation.same_query`, `revocation.paraphrase`,
  `cache.revalidate`, `tenant.isolation`, `tool.authorization`,
  `deletion.cascade`
- **Held-out:** `delegation.chain`, `memory.poison.persistence`,
  `cache.semantic_similarity`, `mcp.tool_scope`,
  `deletion.propagation.cache_memory`, `acl.modify.replay`, `memory.ttl.expiry`

All seven held-out families have executable scenarios under
`src/redfence/bench/heldout.py` and are run separately with
`python scripts/run_heldout.py`; all 12 faults are detected on all 3 templates
(`python scripts/run_template_sweep.py`). The split is still **partial as a
generalisation claim**: seven families over three structural templates of one
synthetic domain, not a large held-out benchmark.

## Licensing and provenance

Original synthetic content authored for RedFence; Apache-2.0. No external
dataset is bundled. A Hugging Face permission-aware enterprise RAG dataset was
observed in the prior-art review but its exact repository, licence, provenance
and schema were **not** verified and it is **not** integrated. Any future
integration requires a compatibility and attribution review.

## Limitations and biases

- Small corpus; retrieval behaviour is bag-of-words and not semantically real.
- English-only, single-domain (fictional SaaS/engineering).
- Template diversity is structural (tenancy, tiers, counts), not linguistic.
- Canaries are synthetic and non-sensitive.
- Permission model is a simplified RBAC + clearance; no ABAC policy language.
- Held-out families are executable, but the held-out set is small; generalisation
  is measured only for these seven families over the three templates.

## Contamination risk

Because families are disjoint by construction, template contamination across
splits is low. Residual risk: a held-out family could share surface wording with
a dev family; this is tracked and must be re-checked if families are added.

## Intended use

Benchmarking and research on stateful RAG/agent authorization. **Not** suitable
for production security assurance claims.
